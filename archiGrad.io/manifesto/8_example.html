example


For the sake of a fair comparison, I assume that both the 3D model and texture are properly optimized: a 4MB .glb model with 3 materials, and a 2MB 8K .ktx2 texture.



| .glb | .ktx2 ─────────────────────────────┼───────────────────────────┼────────────────────────── on-disk MB per project | 4 MB | 60 KB (1) VRAM per project | ~20-25 MB (2) | ~2.5 MB (3) CPU RAM per project | ~20-25 MB (retained) | ~0 MB (released) draw calls per stack | 3 | 1 + 1 per anim bucket shader compiles per project | 1 per material | 0 (shared, one compile total) CPU decode per project | yes (draco + image) | no (BC7 passes through) (5) scaling | O(N) linear | O(N / 34) amortized (4)


(1) An 8192 × 8192 atlas divided into 256 × 256 slices yields 1,024 slots.
At roughly 30 slices per project, that is about 34 projects per atlas.
2 MB on disk / 34 projects ≈ 60 KB per project.



(2) Assume a 4 MB .glb consists of 3 MB Draco-compressed geometry plus a 1 MB embedded 1024 × 1024 PNG texture.
On CPU decode:
  geometry buffers ≈ 15-20 MB (Draco compression ratio ~5-7×)
  texture decoded to raw RGBA: 1024 × 1024 × 4 = 4 MB
On GPU upload:
  geometry: 15-20 MB
  texture: 4 MB + mipmaps (+33%) ≈ 5.3 MB
  VRAM total: ~20-25 MB
The CPU-side copy is retained by default in three.js (not auto-disposed), so add another ~20-25 MB of CPU RAM on top.



(3) One 8K UASTC atlas in VRAM: 8192 × 8192 × 1 byte = 64 MB.
With mipmaps (+33%): ~85 MB.
85 MB / 34 projects ≈ 2.5 MB per project.



(4) The /34 factor comes from atlas packing: a new atlas is only needed every 34 projects. In between, adding a project adds no draw call, no shader compile, and no texture upload — just more sub-rectangles of an existing texture. → amortized cost.



(5) Standard PNG, JPG, and WebP files must be fully decompressed to RGBA (four times their on-disk size) before being uploaded to GPU VRAM. The KTX2 container does not need to be decompressed and is parsed natively in VRAM. BC7 is one such GPU-native block-compressed format that KTX2 can carry.



Only time will tell whether this scaling graph holds up ¯\_(ツ)_/¯



In conclusion, using 3D models can become a serious memory hog even with only a few projects, as filesize scales linearly with project count — and since models are large, they scale large. Textures are small, so they scale small.
